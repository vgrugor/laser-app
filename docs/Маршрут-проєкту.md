# Маршрут проєкту: етапи 1–10

Шість кроків: **Задум → Палітра → Концепція → Генерація → Результат → Збережений виріб**.

Це контракт навігації та каркаса інтерфейсу. Перші два етапи визначають переходи, стани й зберігання; третій додає боковий маршрут і резюме виробу.

| Крок | Умова доступу | Дія / перехід |
| --- | --- | --- |
| Задум | Завжди | Опис, тип і коректні габарити дозволяють перейти до палітри. |
| Палітра | Заповнений задум | Запуск підтверджує палітру й одразу відкриває крок «Концепція», ще до підключення до сервера. |
| Концепція | Є збережений набір, завдання концепцій або підтверджена палітра для заповненого задуму | Тут показано підготовку запуску, виконання, скасування та помилки. Після завершення тут само з’являється набір. Вибір концепції відкриває доступ до генерації. Сам перехід її не запускає. |
| Генерація | Обрана концепція, наявне зображення для повторного запуску або вже створене завдання генерації | Явний запуск відкриває цей крок. Видно стан виконання або помилку. Помилка без нових файлів залишає на генерації, навіть коли є попередні зображення. |
| Результат | Є хоча б одне зображення | Після отримання зображень відкривається цей крок. Частковий результат можна переглянути, але погодити можна лише пару за наявними правилами погодження. |
| Збережений виріб | Користувач погодив актуальну пару зображень | Відкривається після явного погодження. Збереження проміжної версії не замінює погодження. |

## Повернення й відновлення

- Доступний крок можна відкрити повторно. Недоступні кроки заблоковані та мають пояснення.
- Перехід змінює лише `route: {version: 2, current, steps}`. Не змінює `prepared`, концепції, зображення, правки, погодження або час зміни виробу; не запускає SDK.
- Поточний крок зберігається окремо для кожного проєкту в IndexedDB і відновлюється після перезавантаження.
- Якщо збережений крок став недоступним, вибирається найближчий змістовний стан за даними: активна генерація → погоджений виріб → результат → підготовлена концепція → набір концепцій → задум.
- Наявні старі зображення та концепції можна відкривати без повторного підтвердження історичної палітри. Новий запуск концепцій усе одно проходить чинну перевірку палітри.
- Повернення на попередній крок під час генерації дозволене. Перевірка змін даних під час виконання залишається чинною; сама навігація не робить відповідь застарілою.
- Скасування, помилка та частковий результат не позначають виріб погодженим. Повторна перевірка ШІ не переводить користувача з відкритого кроку.

## Стани етапів

Для кожного кроку зберігаються `status` і коротке пояснення `reason`:

| Стан | Значення |
| --- | --- |
| `not_started` — Не розпочато | Для цього кроку ще немає результатів. Доступність кнопки визначається окремо за передумовами. |
| `ready` — Готовий | Рішення або результат кроку вже є. Для «Концепції» це зроблений вибір, для «Генерації» — актуальна пара зображень, для завершення — явне погодження користувача. |
| `running` — Виконується | Є активне завдання ШІ. Створення концепцій відображається на кроці концепції, створення й редагування зображень — на генерації, повторна перевірка — на результаті. |
| `needs_attention` — Потребує уваги | Потрібний вибір чи погодження, не вистачає зображення, параметри змінилися або завдання не завершилося успішно. Пояснення уточнює наступну дію. |

Ці стани обчислюються з даних проєкту й записуються в `route.steps` при збереженні. Вони не є окремим джерелом істини: застарілий кеш не може позначити результат погодженим. Свідомо прийняті зауваження ШІ не заважають стану «Готовий»; сам звіт не змінюється. Невдалий історичний запуск також не скасовує чинне погодження збереженого виробу.

## Оновлення локального сховища

- Версія структури стану — `schemaVersion: 2`, версія маршруту — `route.version: 2`. База IndexedDB та її адреса залишаються попередніми.
- Під час першого оновлення вихідний стан записується під ключем `state-before-route-v2` в об’єктному сховищі `app`. Резервна копія й новий `state` записуються в одній транзакції: помилка або брак місця не перезаписують початковий стан.
- Оновлюються маршрути проєктів і збережених версій; додаються лише відсутні поля. Зберігаються ID, дати, зображення, референси, концепції, вибір, назви версій, примітки, звіти та погодження.
- Під час повторного відкриття міграція не виконується заново. Стани кроків перераховуються з фактичних даних. Сумісний відкритий крок v1 зберігається.
- Старий проєкт без маршруту відкривається за даними; перерване завдання генерації без зображень відкриває генерацію з поясненням. Якщо відсутній активний ID, вибирається перший наявний проєкт.
- Якщо читання чи оновлення не вдалося, подальший запис вимикається для поточного сеансу. Демонстраційні дані не перезаписують старе сховище.
- JSON-імпорт зберігає перевірений набір концепцій та обраний варіант, у тому числі в історії. Чинне правило повторного погодження й перевірки імпортованих зображень залишається в силі.

## Каркас майстерні: етап 3

- Загальна навігація майстерні розташована зверху; колекція проєктів, база знань і каталог типів відкриваються окремо.
- Ліворуч — шість кроків маршруту зі станами та виділеним поточним кроком. Центральна область показує його назву, пояснення та робочий вміст.
- Праворуч — коротке резюме: тип, розмір декору, матеріал, конструкція, доступні кольори та обрана концепція. Зміни параметрів оновлюють резюме без перебудови форми.
- Етап 4 розділяє редактор задуму й палітри. Із результату можна перейти до відповідного кроку через блок «Змінити параметри виробу». Збережений виріб має окремий завершальний екран і створення варіантів.
- Інструменти ШІ згорнуті за замовчуванням. На кроці генерації їх замінено окремим екраном процесу; на попередніх кроках активне завдання показує лише прогрес і скасування.
- Вимоги й ручна перевірка доступні під результатом у розгортуваному блоці. Резюме праворуч містить лише відомості про виріб.
- За ширини до 1000 px маршрут і резюме розташовані над поточним етапом та початково згорнуті. Відкриття іншого кроку знову згортає їх, звільняючи місце для задачі. На ширших екранах вони розгорнуті та залишаються видимими при прокручуванні.
- Зміна ширини перемикає розгортання панелей без повторного створення форми; заповнені поля залишаються на місці. Кнопки загальної навігації мають доступні назви навіть у режимі іконок.

Подальші етапи уточнюють поля й головні дії на кожному кроці, вибір концепцій, прогрес генерації та роботу з результатом.

## Налаштування за кроками: етап 4

- **Задум:** тип виробу та його додаткові поля, опис, габарити декору, конструкція. Необов’язковий референс розгортається окремо. Головна дія — «Далі: палітра»; перевіряються лише умови задуму й габаритів.
- **Палітра:** іменовані зразки доступних морилок та обрамлення. Для одного шару вибір іншого кольору замінює поточний; окрема вирізана рамка недоступна. Для інкрустації збережено обмеження трьох оздоблень та четвертої «Чорної».
- Головна дія палітри — «Створити 10 концепцій», або «Створити нові 10 концепцій», якщо набір уже є. Натискання явно підтверджує видиму палітру для поточної конструкції; повторне модальне вікно вибору кольорів не відкривається. Зміна кольорів чи конструкції скидає підтвердження.
- За наявності концепцій є окрема дія повернення до збереженого набору, яка не запускає ШІ. Перед заміною результату новими концепціями діє наявне попередження.
- Технічні правила застосовуються автоматично й доступні у розгортуваному блоці на палітрі. Тут немає ручної перевірки готового зображення.
- На перших двох кроках відсутні кнопки генерації зображень, редагування та перевірки пари. Активне завдання показує лише прогрес і скасування; невдале створення концепцій показує помилку з можливістю повторити основну дію.
- Під час активного завдання вибір кольорів, обрамлення та повторний запуск палітри заблоковані.

## Вибір концепції: етап 5

- Відкриття кроку показує збережений набір, без повторного звернення до моделі. Кожна картка містить назву, опис композиції, назви та зразки кольорів, спосіб обрамлення. Вибір позначений текстом і `aria-pressed`.
- Над картками — поточний вибір та одна головна дія «Створити зображення». До вибору та під час активного завдання вона недоступна. Проміжний крок «Підготувати завдання» більше не потрібний.
- Вибір не звужує доступну палітру проєкту: інші концепції залишаються придатними до вибору. Під час генерації в запит передаються кольори та обрамлення саме обраної концепції.
- Якщо поточна палітра або одношарова конструкція несумісні з карткою, вона показує пояснення й не може бути обрана. Змінити параметри можна на відповідному кроці без створення нового набору.
- «Створити новий набір» — окрема другорядна дія. Вона попереджає про заміну набору; за потреби перевіряє підтвердження палітри. Новий набір застосовується лише після успішної відповіді й автоматичного збереження попереднього стану у версіях.
- Вибір іншої концепції за наявності зображень спочатку зберігає попередній стан у версіях. Самі файли не прибираються. Нова генерація застосовує отримані результати через наявний механізм завдань; помилка без нових файлів залишає попередні зображення.
- Інструменти ШІ на кроці концепцій показують лише активне завдання або помилку створення набору; дубльованих запусків генерації й ручної перевірки немає.
- На широкому екрані панель вибору залишається видимою під час прокручування карток. На вузькому картки утворюють одну колонку.

Окремі варіанти виробу й захист при зміні вихідних параметрів описані в етапі 8.

## Процес генерації: етап 6

- Окремий екран показує послідовність: **план деталей → підготовка описів → декор → вигляд виробу → перевірка**. Поточний і завершені етапи визначаються за повідомленнями сервера. Відсотків чи прогнозу тривалості немає.
- На початку видно підключення й створення завдання. Помилка підключення або створення завдання залишається на екрані разом із повторним запуском; самі попередні зображення не змінюються.
- Зміни серверного етапу й перелік доступних файлів зберігаються в проєкті. Після перезавантаження браузер відновлює опитування того самого ID; сервер після власного перезапуску повідомляє «перервано».
- Скасування спочатку показує очікування підтвердження. Повторне натискання заблоковане; клієнт не позначає завдання скасованим до відповіді сервера.
- Втрата зв’язку не є підставою для нового запуску. «Відновити зв’язок» отримує стан і результати наявного завдання. Якщо сервер уже завершив роботу, а файли ще не отримано, це зазначається окремо.
- Після успішного завершення відкривається результат. Частково створені зображення також застосовуються зі збереженням попереднього стану у версіях; якщо є лише новий декор, спочатку відкривається він, а не старий вигляд виробу.
- Помилка без нових файлів залишає на екрані генерації. Попередні зображення доступні через окрему дію перегляду. Кнопка повторної генерації запускає весь процес спочатку; автоматичного чи прихованого відновлення з середини немає.
- Якщо з цього самого завдання отримано актуальну пару зображень і план, а зупинилася лише перевірка, доступна дія «Повторити лише перевірку». Вона не генерує зображення знову.
- Зміна проєкту під час виконання зберігає наявний захист: застаріла відповідь не підміняє актуальні дані. Повторний запуск залишається явною дією користувача.

## Перегляд, правки й прийняття: етап 7

- Зображення розташоване в центрі з перемикачем «Увесь виріб / Декор для обведення» та збільшенням. Праворуч — стан перевірки, основні зауваження й рішення користувача. Резюме параметрів тут згорнуте.
- Основні дії — «Прийняти виріб» і «Внести правки». На вузькому екрані вони розташовані під зображенням; одночасно видимий лише один набір цих кнопок. Зауваження переносяться нижче.
- Перші два зауваження показані одразу, решта розгортається. Художня перевірка й ручні перевірки креслення доступні окремо. Повторна перевірка ШІ не генерує зображення.
- «Внести правки» відкриває редактор під зображенням. Можна ввести опис, додати всі зауваження ШІ та вказати рішення, які потрібно зберегти. «Застосувати правки» записує інструкції й одразу запускає один цикл редагування, оновлення вигляду та перевірки.
- Чернетка `resultDraft` зберігається без зміни погодження, дати редагування виробу та відбитка завдання. Вона переживає перемикання видів і перезавантаження; до застосування її текст не передається в запит до ШІ. Після прийнятого сервером запуску текст чернетки очищається, а застосовані побажання залишаються в проєкті. При помилці запуску чернетка залишається доступною.
- Погодження попри зауваження ШІ використовує наявне явне підтвердження з коментарем і копією звіту. Відсутні чи застарілі зображення, ручні позначки «Потрібна правка» та активне завдання блокують прийняття. Незастосований текст чернетки не змінює самі зображення.
- Історія версій, власна ручна оцінка, файли, план і промпти розгортаються за потреби. Збереження й відновлення версій, завантаження зображень, ручне додавання файлів та експорт JSON залишаються доступними.
- Оновлення стану ШІ не перебудовує форму правок і не скидає розгорнуті зауваження. Погодження переводить до збереженого виробу; його окремий завершальний екран належить етапу 9.

## Повернення та окремі варіанти: етап 8

- Повернення маршрутом лише відкриває відповідний крок. Зображення й прийняття зберігаються, доки користувач не змінює дані.
- «Створити окремий варіант» копіює задум, набір концепцій і зображення у нову чернетку. Вона має власну історію й перевірки, номер у сімействі та посилання на вихідний проєкт. Успадковані зображення позначені до отримання нового результату.
- «Інша концепція з цього набору» відкриває ті самі 10 концепцій у новому проєкті без вибору та зображень. Попередній виріб залишається у колекції.
- Зміна параметрів, палітри, концепції, референсу, ручних позначок, застосування правок або запуск ШІ для прийнятого виробу створюють окремий варіант. Відновлення історичної версії також не підміняє прийнятий оригінал. Редагування параметрів проєкту з активним завданням відгалужує чернетку; вихідне завдання продовжує працювати зі своїми даними.
- Перед першою зміною параметрів звичайної чернетки з результатом зберігається версія. Зміни позначають зображення як такі, що потребують оновлення. Збережений набір концепцій залишається доступним, із поясненням зміни задуму або палітри.
- Перед генерацією після зміни завдання показується окреме підтвердження поточного задуму, габаритів та доступних морилок. Скасування не запускає ШІ. Підтвердження прив’язане до поточних даних, тому наступна зміна вимагає нового перегляду. Несумісні з палітрою чи конструкцією концепції залишаються заблокованими.
- Походження варіанта зберігається в експорті JSON. Після імпорту посилання на вихідний виріб показується лише за наявності цього проєкту в локальній колекції.

## Збережений виріб: етап 9

- Після погодження відкривається окремий завершальний екран: дата рішення, погоджена пара зображень, параметри, оздоблення та файли для повторного виготовлення. Редактор правок і панель запусків ШІ тут приховані.
- Декор і вигляд завантажуються окремими кнопками. «Резервна копія проєкту» експортує наявний JSON із вкладеними зображеннями, історією, планом і рішенням користувача. Зберігання в браузері не називається резервною копією.
- Паспорт виробу завантажується у TXT: тип, розмір декору, матеріал, конструкція, обрамлення, кольори, орієнтовний план деталей, чорне гравіювання, ручні перевірки, побажання й прийняті зауваження. Файл призначено для підготовки креслення та повторення виробу.
- Морилки беруться з плану деталей, за його відсутності — з обраної концепції. Якщо немає й концепції, палітра явно названа доступними морилками проєкту. Інтерфейс не видає весь початковий набір кольорів за фактично використаний.
- План деталей ШІ позначено орієнтовним; кількість, поділ та кольори потрібно звірити із зображеннями. Невизначені дані старих проєктів не вигадуються: відсутня дата або план відображаються як відсутні.
- Окремо показано перехід до SolidWorks і LightBurn. Погодження зовнішнього вигляду не означає готовності растра до різання. Ручні перевірки зі звіту та плану зведено без повторень.
- Зауваження та коментар користувача читаються зі звіту, зафіксованого під час погодження. Історія версій залишається доступною. Зміна прийнятого результату відбувається через окремий варіант; є повернення до колекції та вибір іншої концепції з того самого набору.
- Перегляд і завантаження не змінюють дату редагування, погодження або зображення та не запускають ШІ. Повернення до попередніх кроків і створення варіантів працюють за правилами етапу 8.

## Наскрізна перевірка та завершення: етап 10

Виправлено переходи й відображення станів, виявлені під час перевірки всього маршруту:

- Якщо після завершеної генерації змінилися параметри, на кроці генерації показується «Зображення потрібно оновити» та дія «Оновити зображення». Етапи нового запуску очікують, а виконання старого завдання не видається за актуальний прогрес. Попередні файли залишаються доступними. Невдалий або перерваний запуск зберігає власний стан і можливість повтору.
- Помилки створення завдання концепцій зберігаються в проєкті й показуються розгорнутими на попередніх кроках, у тому числі після перезавантаження. Під час підключення відображається очікування запуску. Втрата зв’язку з поточним завданням пропонує відновлення підключення до того самого ID.
- Помилка запуску повторної перевірки відображається біля результату. Вона не стирає останній режим роботи із зображенням: повтор редагування залишається редагуванням.
- Службове поле `aiLaunchErrorAction` позначає дію, до якої належить повідомлення, не впливає на відбиток завдання та не передається моделям. Новий варіант починається без цих помилок.

Перевірено:

1. Новий проєкт → задум → палітра → помилка запуску концепцій → повтор → 10 концепцій → вибір → пара зображень → погодження попри зауваження → збережений виріб.
2. Паспорт TXT із коментарем користувача та JSON із двома вкладеними зображеннями, історією й погодженням.
3. Інша концепція з того самого набору у власній чернетці; повернення до погодженого оригіналу; генерація варіанта; зміна задуму й коректне оновлення стану генерації; скасування підтвердження без нового запуску.
4. Відновлення стану після перезавантаження та ширина 320 px без горизонтального переповнення сторінки.

Браузерний сценарій виконувався з фактичним кодом застосунку, ізольованим сховищем і підставними відповідями моделей. Реальна генерація через підписку не запускалася; користувацькі проєкти не змінювалися. Тимчасову браузерну сторінку прибрано після перевірки.

Автоматично пройшли 88 тестів, зокрема спільний сценарій модулів маршруту, клієнта, погодження, паспорта й варіантів (`tests/route-flow.test.mjs`). Синтаксис модулів перевірено. Окремий тест `local HTTP lifecycle, anti-CSRF, cancellation and restart recovery` потребує відкриття локального порту й у поточному середовищі завершується `listen EPERM`; він не включений у ці 88 успішних тестів.

## Негайний перехід до концепцій

- Після підтвердження запуску з палітри крок «Концепція» відкривається ще до підключення та створення серверного завдання. Палітра не залишається активним кроком очікування.
- До готовності набору відображаються підготовка/очікування, поточне завдання та скасування. Після помилки або скасування можна повторити запуск на цьому самому кроці. Старий набір при повторній генерації зберігається до успішного застосування нового.
- Після перезавантаження активне завдання концепцій залишається доступним на кроці концепцій, навіть якщо в історичному проєкті немає окремого підтвердження палітри. Повернення до палітри вручну дозволене й не скасовує завдання.
- Перевірено в браузері на ізольованих даних: негайний перехід, перезавантаження під час роботи, скасування, повторний запуск і поява десяти карток. Пройшов 91 автоматичний тест; обмеження серверного тесту з відкриттям порту залишається описаним вище.

## Фільтр історії версій

- На екранах результату й збереженого виробу історія має перемикач «Лише різні зображення / Усі версії». Після завантаження застосунку типовий режим — «Лише різні зображення»; вибір режиму зберігається під час поточного сеансу інтерфейсу.
- Для кожної однакової збереженої пари `master + preview` показується найновіша версія. Збіги групуються по всій історії, навіть коли між ними були інші результати. Порівнюються збережені дані/посилання зображень; аналіз візуальної подібності не запускається.
- Зміна будь-якого з двох зображень утворює окрему картку. Часткові результати з одним зображенням також показуються; версії без зображень приховані лише у відфільтрованому режимі.
- Показано кількість видимих карток і загальну кількість версій. Для групи зазначено кількість збережень з цією парою. Картка зберігає ID, номер, назву, дату й погодження фактичної найновішої версії; її перегляд і відновлення працюють звичайним способом.
- «Усі версії» повертає повну історію разом зі змінами параметрів, перевірок і версіями без зображень. Фільтр не видаляє збереження, не змінює ліміт 20 версій, погодження, експорт або поточний проєкт. Перемикання оновлює лише список і залишає історію розгорнутою.

## Історія генерацій концепцій

- Позначки на картках прив’язані до незмінного `concept.id` із конкретного набору. Новий набір отримує інші ID навіть для тих самих номерів або назв. Під час запуску до завдання записуються ID та назва концепції з фактичного запиту.
- `conceptRuns` зберігається окремо від історії версій у локальному проєкті. Запис містить ID спроби/завдання, концепцію, проєкт, дію, дати, стан, помилку та зображення, отримані саме в цій спробі. Застарілий вигляд із попереднього запуску не доповнює частковий результат до пари.
- Картки показують активне створення, наявну пару зображень, частковий результат або невдалу/скасовану спробу. Успішна попередня генерація залишається позначеною після пізнішої невдалої спроби. Дата останньої спроби відображається окремо.
- «Відкрити результат» відкриває архівну пару або частковий результат у вікні перегляду. Вона залишається доступною після зміни поточних зображень і видалення старих знімків за лімітом 20 версій. Перегляд не змінює вибір концепції, погодження чи дані проєкту.
- Перелік спроб збирається з локальних проєктів за точним ID концепції, з усуненням повторів за ID спроби. Окремі варіанти успадковують концепції зі збереженням ID та починають власний журнал спроб. Тому вихідний набір бачить результати, створені в його варіантах.
- Знімки версій не копіюють журнал спроб. Відновлення версії зберігає чинний журнал, тому не скидає відомості про вже виконані генерації. Журнал і архівні зображення включаються в JSON-експорт; також додаються записи інших локальних варіантів для концепцій цього проєкту. Імпорт перевіряє зображення та метадані; активні імпортовані спроби позначаються перерваними й не запускаються автоматично.
- Клієнт передає моделям завдання без журналу генерацій. Повторна перевірка ШІ не створює нової спроби генерації.
- Після підключення до сервера клієнт намагається відновити минулі спроби за ID завдань, які залишилися в поточних проєктах або версіях. Сервер читає точний вибір зі збереженого `request.json`, а клієнт завантажує оригінальні файли результату. За відсутності підтвердженої прив’язки позначка не вгадується за поточним вибором чи номером. Для відновлення минулих запусків потрібен перезапуск сервера з оновленим кодом; нові запуски фіксуються клієнтом одразу.
- Перевірено 108 автоматичними тестами та у браузері на ізольованому наборі: позначки різних станів, результат з іншого варіанта, перегляд без зміни вибору, нова генерація, новий набір без успадкованих позначок, відновлення версії та ширина 320 px. Під час браузерної перевірки відповіді моделей підставні; робочі проєкти не змінювалися.
