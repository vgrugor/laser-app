# Сценарій та стани

## Основний маршрут

1. **Задум.** Координатор читає вхід, вибирає файли бази, фіксує відомі параметри та припущення. Для концепцій допустимі невідомі габарити; для детальної генерації потрібен цільовий розмір і палітра. Запитувати тільки те, без чого рішення суттєво зміниться; безпечне припущення явно показувати.
2. **Концепції.** Автор готує 10 справді різних текстових карток. Координатор показує їх користувачу.
3. **Вибір.** Чекати прямого вибору користувача. Не трактувати тишу або рекомендацію агента як вибір. Дозволено поєднати картки; записати фактичну редакцію задуму.
4. **План.** Конструктор визначає частини, оздоблення, операції, обрамлення та фурнітуру. Художній редактор перевіряє заплановану композицію. Обов'язкові перевірки плану можуть бути виконані програмно в майбутньому, але не підміняють перевірку зображення.
5. **Фронтальний майстер.** Автор промпту готує інструкцію, генератор створює чистий фронтальний растр. Він спочатку внутрішній: користувач не мусить погоджувати кожну проміжну операцію.
6. **Перевірка майстра.** Технічний перевіряльник і художній редактор читають фактичний файл. Результат із блокувальними помилками не йде у фінальний комплект без явного позначення проблеми.
7. **Вигляд виробу.** За придатним майстром генератор створює вигляд усього виробу; обидва перевіряльники оцінюють його та відповідність майстру. Фурнітуру й кольорові області не вигадувати заново.
8. **Перегляд користувачем.** Показати готовий виріб, фронтальний декор і короткий звіт. Користувач погоджує або задає правки. Розширений промпт доступний, але читати його для роботи не обов'язково.
9. **Збереження.** Після прямого погодження створити незмінний комплект: обидва фактичні зображення, план, промпти, перевірки, версії правил і палітри, підтвердження користувача. Не перегенеровувати фронтальний майстер після погодження без нової правки.

Таким чином користувач оцінює весь виріб, а фронтальний майстер служить джерелом його декору. Це технічний порядок прототипу для зменшення розбіжностей, а не вимога показувати декор раніше виробу.

## Стан виконання та стан приймання

Це дві різні властивості. `workflow_state` описує поточний крок; `acceptance_status` — що реально підтверджено.

| workflow_state | Наступний крок |
|---|---|
| draft | Уточнення або підготовка концепцій |
| concepts_ready | Показати 10 карток |
| awaiting_concept_choice | Чекати вибору користувача |
| planning | Створити й перевірити план |
| generating_master | Створити фронтальний файл |
| reviewing_master | Перевірити фактичний майстер |
| generating_preview | Створити вигляд виробу за майстром |
| reviewing_pair | Перевірити пару |
| revising | Виконати конкретну правку й перевірити залежні результати |
| awaiting_user_review | Показати файли та прийняти відповідь |
| needs_user_input | Потрібна конкретна інформація або рішення; незалежна робота можлива |
| paused | Користувач зупинив роботу |
| saved | Затверджений комплект збережено |
| failed | Операція не вдалася; зберегти попередній результат і запропонувати відновлення |

`acceptance_status`: concept / visually_approved / geometry_verified / manufactured_verified. Агенти самі не ставлять останні два статуси за красивим растром. Підтвердження користувача й геометрична перевірка зберігаються як докази; перехід до наступного статусу не виводиться з попереднього.

Під час уточнення геометрії користувач може почати окрему пізнішу роботу; поточна перша версія закінчується візуально схваленим комплектом.
