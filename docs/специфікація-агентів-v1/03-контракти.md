# Контракти даних

Це контракт прототипу, а не реалізований API чи повна JSON Schema. Файли у шаблонах показують форму; null означає невідоме або ще не заповнене значення. Координатор має перевіряти поля перед передаванням.

## Project

`id`, `revision`, `workflow_state`, `acceptance_status`, `brief`, `knowledge`, `selected_concept`, `locked_decisions`, `design_plan`, `assets`, `reviews`, `approvals`, `run_policy`.

- `knowledge`: версія бази, SHA-256 її manifest.json, SHA-256 палітри, список реально застосованих файлів. Перед виконанням заповнити hashes фактичними значеннями, не вигадувати.
- `brief`: оригінальний запит, тип виробу, об'єкти, розміри виробу й декору, референси, припущення, невизначеності. Висота може бути null для плоского виробу.
- `locked_decisions`: ID, опис рішення, джерело (користувач/затверджена версія), область застосування, дата. Автоматичне рішення ролі не прирівнювати до прямого погодження.
- `approvals`: actor=user, тип погодження, точний перелік версій/файлів, текст підтвердження, дата. Погодження старого зображення не переходить на нову версію автоматично.

## DesignPlan

`revision`, `palette_ids`, `product_dimensions_mm`, `decoration_dimensions_mm`, `parts`, `engraving`, `frame`, `hardware`, `composition`, `parts_estimate`, `manual_checks`.

Для `parts`: id, name, layer (backing/top/body), finish_id, quantity, position_description, cut_boundary_notes. Один запис може описувати quantity однакових фізичних частин, але не приховувати розділені фрагменти в одній одиниці.

Для `engraving`: id, surface_part_id, description, color=black, operation=engrave. Для `frame`: method (engraved/cut/none), part_ids, finish_id, target_width_mm; ширина гравіювання та ширина вирізаної деталі мають різний зміст. Для cut перевіряти задану ширину ≥2 мм; цього недостатньо для доказу фактичної геометрії.

Для `hardware`: відома модель або статус illustrative, кількість, розміри якщо відомі, розташування, невизначені питання кріплення. Для `parts_estimate`: min/max/null, basis=plan або observed_image, backing_count і body_count окремо.

## Task

task_id, project_id, project_revision, role, purpose, inputs, expected_output, constraints, return_to. Завдання посилається на конкретні версії. Невідповідна поточному проєкту відповідь не може замінити актуальні файли.

## Asset

id, revision, kind (master/preview/reference), path, sha256, plan_revision, parent_asset_ids, prompt, created_at, tool_result, pixel_dimensions. kind=reference не є автоматично затвердженим результатом.

Файли мають бути збережені та доступні для перегляду. Один лише шлях без наявного файла не є успішним asset. SHA-256 заповнюється після збереження; його зміна означає інший вміст.

## Review

reviewer, scope (plan/master/preview/pair), project_revision, plan_revision, asset_ids, disposition, findings, manual_checks.

`disposition`: pass_visual / changes_required / not_checked. Для плану pass_visual означає лише прийнятність плану, а не огляд зображення; scope зберігає це розрізнення.

Для `findings`: id, severity (blocker/advisory), rule_ref, location, observation, method (plan_check/visual_inspection/geometry_measurement/user_confirmation), evidence_asset_ids, route_to, suggested_action. Невиконані перевірки й невідомі розміри записувати у manual_checks, а не позначати pass.

route_to: constructor / prompt_author / generator / coordinator. Аргументована технічна помилка має перевагу над позитивним художнім висновком; незгода ролей не вирішується голосуванням.

## Зв'язність

ID оздоблення належить фактичній палітрі; ID частини, asset і concept існують; всі reviews стосуються поточних версій. Два reviews різних asset не утворюють перевірену пару без pair-перевірки. Завдання на preview посилається на перевірений master і ту саму редакцію плану.
